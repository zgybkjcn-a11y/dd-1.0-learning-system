## 2. 已核实的主要缺口

### 2.1 文档入口过时，发布状态分散

[docs/README.md](README.md) 仍以“14 道题、首次绑定待操作”为当前状态，并在后文称 HTTPS/桥接待实施；[复用入口](open-webui-reuse/README.md) 仍以 11-04 状态为主。[恢复指令](goal/RESUME-SESSION-2026-11-07.txt) 的三个小样本仍写“尚未实现”，后续报告则已实现。旧记录保留历史合理，但缺少统一的新入口会直接导致误操作、重复安装、重复测试和错误估算。

服务镜像、主站静态快照、Tool 数据库里的版本、内容清单分开管理是现实需要，但目前缺少一个统一的兼容组合清单。现有注册脚本明确拒绝覆盖不同内容，不能把“运行旧注册脚本”当作 Tool 1.1.0 升级路径。

### 2.2 教材阅读覆盖与教学内容覆盖差距很大

本次从目录与数据文件核对：**13 册、98 个目录区间；60 道应用题加既有 14 道起步题共 74 道；20 道题有精确概念映射，概念共 18 个。** 数学概念为二上 6 个、七上 12 个；其余 11 册没有同等概念映射。60 道应用题只分布在二上第二/三/五单元、七上第二/五章，每范围 12 道、每档 4 道。

一个档位恰好 4 道题，达到四题升档条件时通常也已耗尽该档题，后续新题验证和间隔复习选择较少。优先补齐当前章的知识覆盖与已有题映射，再按明确薄弱点增加变体，价值高于单纯增加总题数。非数学当前主要为阅读问题串，不能用“开设七门学科”表述成七门完整辅导能力。

二下数学 106 页离线 OCR 已完成，但完整页双重审核通过数仍为 **0**。当前应推进分批复核、记录图形/单位/错例上下文，而不是重新做 OCR 或直接扩大入库。5 个助手核对片段不是 5 张完整审核页，更不代表二下审核有进展。

### 2.3 现有教材检索有章内召回不足的结构性条件

[login_gateway.py](../learning_service/login_gateway.py) 先向整册固定集合请求 `k=40, hybrid=False`，再由 `bounded_references` 过滤章内页码。**如果章内相关页未进全书前 40，过滤后会为空；空结果不能据此证明本章没有内容。** 本次离线合成 40 个章外候选加第 41 个章内候选，截断后返回 0 页，保留章内候选时返回 1 页。没有调用真实检索服务，未量化线上发生频率。

还应分别验证：相关性排序与最终按页码展示、重复分块占用候选、同义表述、术语多义、低相关命中和无证据情形。页级 ID 解决身份，不解决召回与相关性。

### 2.4 20/20 离线开发问句不代表真实提问覆盖

对 [片段样本](../scripts/textbook_passage_sample.py) 新增几种未配置的说法，仅本地查询：

| 提问 | 实际结果 | 暴露的问题 |
| --- | --- | --- |
| 有理数加法的法则是什么？ | 加法片段 | 已有词项正常命中，作为对照 |
| 什么叫倒数？ | 倒数片段 | 已有词项正常命中，作为对照 |
| 把两个同号数合在一起，结果的符号跟谁走？ | 无证据 | 同义说法未召回 |
| 两个数的积等于 1，它们是什么关系？ | 无证据 | 与“乘积是1”的字面匹配不足 |
| 有理数相乘时怎么判断正负？ | 无证据 | 日常表达未命中符号规则 |
| 乘法能不能对加法展开？ | 只命中加法法则 | 关键词“加法”命中，预期的分配律未命中 |

这些是小规模问题定位，不能据此给出总体准确率。下一步需固定独立评测集，先记录召回问题，再改检索，不应每看到一个失败问题就加同义词并宣布测试通过。

### 2.5 证据链尚未进入真实聊天闭环

当前 Tool 1.1.0 候选只接受页级位置；5 个已核对片段在独立脚本，服务路由未读取它们。离线正文检查只允许逐字引文，没有通用的“断言是否得到原文支持”判定。真实模型是否调用工具、是否用到正确引用、是否把本地讲解称为教材原句，均未验收。

把片段接入服务端时，要由服务器固定材料清单、选择范围和当前日期，并在每次查询检查启停/失效；不能把离线 CLI 的 `--as-of`、路径、清单哈希交给聊天模型选择。还要分开授权访问与内容身份：公开来源 ID 不应成为绕过当前档案检查的入口。

### 2.6 登录异常恢复有效，但根因仍不明确

此前家长报告 `LEARNING_IDENTITY_MISMATCH`，重新进入后恢复。源码将学习会话非 200、服务端上下文格式不符、身份不符统一映射到这个错误，无法从错误码区分过期、故障和真正的身份冲突。Tool `_run` 又把全部失败统一成“请确认登录与范围”。这有利于减少内部信息外露，但不利于定位普通故障。

改进应为不含身份/凭据的内部分类码和请求关联标识，配套准确的恢复文案，而不是重绑或在日志里打印 Cookie。已有防跨档案、前后 revision 核对、CSRF、固定服务地址等边界有测试，继续保留。

### 2.7 测试丰富，但干净环境复现有具体缺口

- [requirements-dev.txt](../requirements-dev.txt) 仅引入运行依赖与 pytest，没有 TestClient 所需的 `httpx`，也未声明浏览器测试依赖；已安装包元数据显示 `httpx` 属于 FastAPI/Starlette 的可选 extra，并非当前基本依赖自动保证。
- [数学参考测试](../tests/test_math_references.py) 指向被 Git 忽略的本机教材目录；多个主站测试复用它。新克隆仓库缺少这些材料时，不能直接复现本机结果。
- 浏览器测试使用 `pytest.importorskip`，且部分代码固定 `/usr/bin/google-chrome`；缺依赖可能跳过关键流程，换系统路径可能失败。
- 仓库未跟踪 `.github` 工作流；未查询远程是否另设外部 CI。不能仅以本机测试通过推断推送后有自动验收。
- `learning_service/app.py` 在模块导入结尾执行 `app = create_app()`，会读环境、建目录/数据库。未来测试与工具应能只导入业务函数而不初始化默认运行状态。

积极结果：通过静态路由对照，当前 OpenAPI 文件是 **71 paths / 24 schemas**，71 条路径与源码声明一致，没有发现路由集合差异；过时的是说明文字仍称 66/24。新增证据字典仍缺精确响应模型与跨服务契约检查，不能把路径一致等同于所有字段类型已覆盖。

### 2.8 恢复与监控已有基础，完整运营证据不足

已有数据库/附件备份、隔离恢复、撤销恢复后会话、暂停 provider 等代码和历史验证，不能再列为“从未做备份”。但完整架构恢复仍主要是设计：学习数据、WebUI/向量数据、静态/Tool 版本、教材原件、证书/秘密、备份后删除与费用记录、固定镜像需要形成对应集合。

[backup.py](../learning_service/backup.py) 如未停写，只声明“在线数据库快照 + 顺序复制附件”；它没有建立数据库与并发附件修改的同一时间点一致性。恢复只重放快照内删除记录，缺少备份之后的删除增量。监控模板未正式启用的记录仍有效；当前活动家庭 Compose 没有监控服务，独立外部监控是否配置未核查。聊天费用也未纳入学习服务台账。

本家庭规模可以先落实基本备份和可恢复性，不必把完整商业运维、跨站容灾或多租户监控作为现有功能使用前置。
